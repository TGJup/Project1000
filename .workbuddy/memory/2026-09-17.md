### 第五轮：用户追问两件事（串口3 想改回原版 / 串口1 打包发送到底会不会错）

**A) 串口3 想改回"严格查询式、不要超时"**

重要事实：**原版 USART3_LoopCall 已被我覆盖，本地无备份、无 git，无法逐字还原。**
只能按当时记录的语义重写。按记录，原版等价于：

```c
if(USART3_RxFinish == 1) { if(USART3_EP_RE(&Read_data)==5) Packet_Ready_flag=1;
                           U3_wait_ack = 0; USART3_RxFinish = 0; }
if(U3_wait_ack == 0 && (tick_now - U3_last_tick) > EP_Send_Cycle)
{
    EP_Packet_Make(EP_CMD_0x90_ASK);   // 返回值不管
    U3_last_tick = tick_now;
    U3_wait_ack  = 1;                  // 无条件置 1
}
```
→ 与现版的差别只有两处：① 去掉 100ms 超时解锁那 4 行；② 把 wait_ack=1 从
`if(EP_Packet_Make(...)==0)` 里提出来无条件执行。

结论：**技术上能改，但不建议**。原因见下。

**关键澄清：超时解锁 ≠ 超时重发。**
现版超时（100ms）后只是松开锁，仍必须再等满 30ms 节拍才发下一次查询，
**同一次查询里绝不会补发第二帧**。所以它 100% 还是查询式，只是"丢一次应答不会卡死"。
去掉超时的代价：应答丢一次（噪声/ORE 残留/帧被截断/校验错）→ wait_ack 永远为 1
→ 永久停查 → Packet_Ready_flag 永远 0 → **USART1 在正常阶段一帧都不发，飞控看到完全静默**，
且无法自恢复，只能复位 MCU。

**9600bps 下 30ms 节拍本身就很紧**：13 字节 = 13.5ms，查询 13.5ms + 应答 13.5ms ≈ 27ms
一问一答就占满节拍。所以 wait_ack（等应答再发下一次）是必要的，
"每 30ms 无条件发一次查询、完全不等应答"那种写法在这里会和对端应答撞车，不可取。

**B) 串口1 "打包→算校验和→发送"到底会不会错**

用户的直觉**部分正确**。仿真脚本：`.workbuddy/tmp/tx_corrupt_sim.py`

机制（HAL 源码实锤）：
- `stm32f1xx_hal_uart.c:1321` → `huart->pTxBuffPtr = pData;` **只存指针，不拷贝数据**
- `stm32f1xx_hal_uart.c:3544` → `huart->Instance->DR = (uint8_t)(*huart->pTxBuffPtr++ & 0xFF);`
  **每来一次 TXE 中断，从调用者的数组里现取一个字节**
→ 所以 19 字节不是"一次性交给硬件"，而是在 **1.649ms**（19×86.8µs @115200）里
  一个字节一个字节从 `USART1_TXBuffer` 读出去 → **这 1.649ms 内该缓冲区必须冻结。**

仿真结论（主循环周期 0.1 / 0.5 / 1.0 / 1.6 / 2.0 / 5.0ms 各跑一遍）：
| 场景 | 忙时改写缓冲区次数 |
|---|---|
| 正常 80ms 节拍稳态（8s） | **0（全是 0，不受主循环周期影响）** |
| 零帧阶段（原版缺 U1_last_tick 刷新） | 28125 / 4500 / 1500 / **0 / 0 / 0** |

- **用户直觉对的地方**：正常 80ms 节拍下，`tick_diff >= 80ms` 这个门限本身就把
  1.649ms 的危险窗口躲开了，真的撞不上。所以原版在稳态下不会出错。
- **真正会出错的地方**：零帧阶段。原版那段 `tick_diff` 恒成立 → 每轮主循环都发
  → 帧率被发送耗时顶到约 600 帧/秒 → 只要**主循环周期 < 1.649ms**，缓冲区就一直被改在空中。
  零帧内容恒定所以看不出来，**真正的风险在 3 秒切换瞬间**：那一刻 `tick_diff` 是个很大的值，
  只要 `Packet_Ready_flag` 已是 1，正常帧立刻开始打包，而空中很可能还有一个零帧没发完。
- 抓出来的污染帧（把"第 5 字节后改写"那一刻的空中字节流dump出来）：
  ```
  实收  : EB FE 00 00 00 B8 30 39 00 00 01 F4 02 58 3A 98 80 E8 B7
  正常帧: EB FE 01 18 0B B8 30 39 00 00 01 F4 02 58 3A 98 80 E8 B7
  帧头 EB FE 通过，但校验和算得 0x93、实收 0xB7 -> 飞控丢弃
  ```
  这就是"打包好再算校验和"救不了的原因：**校验和是在内存里、某一个时刻算的；
  而硬件是从同一块内存里、跨 1.649ms 逐字节搬的，两者看到的不是同一时刻的数据。**
- 另一个与污染无关、但语义确实错的小毛病：忙时 `UART_SendData` 返回 1，
  原版既没接返回值、调用处还照样清 `Packet_Ready_flag` 并推进 `U1_last_tick`。

**结论**：我改成"第一行判忙"之后，`FC_Packet_Make` 变成自洽的 ——
要么完整写入并交出去，要么一个字节都不碰直接返回 1。这样就不需要证明
主循环周期有多快、时序怎么排，"发送中被改写"在结构上不可能发生。
